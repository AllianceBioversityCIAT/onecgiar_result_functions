# Breaking changes & new capabilities

| **Date** | **Change** | **Action required** |
| --- | --- | --- |
| **2026-11** | ⚠️ **Changed:** contributing partners are linked only by `institution_id` or an **exact** name/acronym that matches one CLARISA institution. Partial names are no longer matched, and CGIAR centers are never linked as partners. Every partner that is not linked comes back in `outcomes[].warnings` (`partner_unresolved`, `partner_ambiguous`, `partner_is_cgiar_center`), and the result is still created. Before, those partners were dropped silently or linked to the wrong institution. See **Contributing partners → How a partner is linked**. | **Yes, if you send names.** Send the CLARISA `institution_id` for each partner, and read `warnings` on every response row. |
| **2026-11** | **Fixed:** ToC mapping. `result_indicator_description` and `result_indicator_type_name` now narrow the match together, and the pick is deterministic. Sending the type no longer links the result to an indicator of another ToC result. See **ToC mapping → How the indicator is matched**. | None. If you stopped sending `result_indicator_type_name` as a workaround, you can send it again. |
| **2026-11** | **Clarified:** how to get valid bilateral project codes. Use `https://api.clarisa.cgiar.org/api/projects?phase=2026`, where each project has one unique `external_code`, or check one code with `&code=`. Past-phase rows in the unfiltered list are not accepted, and codes are not carried across phases. Missing or duplicated projects are corrected in the W3 Registry, not in PRMS. See **Contributing bilateral projects → Finding the project code**. | None if you already send current-phase codes. Otherwise, refresh your project list from the `phase=2026` endpoint. |
| **2026-11** | **New:** correct a **Knowledge Product** that is **Rejected** or in **Editing**. Send it through `POST /ingest` with `data.result_code` and the **same handle**. PRMS replaces the fields you own (centers, ToC mapping, partners, bilateral projects, lead contact person) on the same record, and re-reads title, description, geography and metadata from CGSpace, ignoring the payload values. A Rejected KP returns to **Pending Review**. A KP in Editing follows `keep_editing`. Before this change, every KP sent with `result_code` was refused with `409`. See **Result code → Correcting a Knowledge Product**. | None to keep ingesting. To fix a rejected KP, resend it **with** its `result_code` and the same handle: without the code you create a duplicate. Approved, Pending Review and previous-phase KPs are still refused with `409`. |
| **2026-10** | **New:** resubmit a **rejected** result. Send the corrected result through the same `POST /ingest` with `data.result_code` set to the code of the rejected result. PRMS replaces the data **on the same record** (same result code) and returns it to **Pending Review** (`operation: "updated"`). Only results **Rejected** in the current phase can be resubmitted: any other status is refused with `409`. There is no `PATCH` endpoint. See **Result code** below. | None to keep ingesting. To fix a rejected result, resend it **with** its `result_code`: without the code you create a second, unrelated result. Send the **complete** result: a section you leave out is cleared, not kept. |
| **2026-10** | **New:** `data.result_code` on `/ingest`. Send the code of a result you reported and had approved in a previous phase, together with the full result, and PRMS creates its version in the current phase with **your new data** and the **same result code**. The prior-phase record is not modified. The code can be sent as a string (`"28565"`) or as an integer (`28565`). Also: the `op` field is not read, so `update` and `delete` are not implemented. | **Action required:** None to keep ingesting: without `result_code`, nothing changes. Use it instead of `/version` when you already have the new phase's data, so you don't need a second step to complete the result. |
| **2026-09-24** | **Innovation Use MDS relaxed:** quantitative measures may be omitted or sent as an empty array. When `innov_use_to_be_determined` is `true`, measures are ignored; otherwise, a non-empty list must contain at least one row with both a non-blank `unit_of_measure` and numeric `quantity`. `organization` is optional and is not an MDS requirement. Bilateral project budgets are optional; the project `grant_title` remains required. Reporting stores an omitted or zero budget as yet to be determined. | **Action required:** stop treating measures or bilateral project budgets as required. Keep sending at least one identified bilateral project. If a measure is sent for known use, include one complete row. |
| **2026-09** | **Partially superseded on 2026-09-24; see the update above. ⚠️<br>Breaking:** `contributing_bilateral_projects[].grant_title` must now resolve to a project of the **current reporting phase**, and is matched by registry **code** first. Send the CLARISA project `code` on its own — not the full title, and not code and title concatenated. A value that resolves to nothing is now **rejected with 400**. <br><br>⚠️ **Superseded on 2026-09-24; see the update above.** Innovation Use previously required investment data for every `contributing_bilateral_projects[]` entry: a positive `usd_budget` or `is_determined: true`. \| **No action required.** `usd_budget` and `is_determined` may now be omitted. Reporting treats an omitted or zero budget as yet to be determined; every project must still include a resolvable `grant_title` | **Yes, if you send project titles.** A concatenated or title-only `grant_title` used to match a legacy catalogue row under an old phase: the result and its investment were saved against a project no PRMS screen can show, which looked exactly like nothing being saved. Both new investment blocks are optional and outside the MDS. An amount on `contributing_programs[]` is still not stored — complete it in PRMS. |
| **2026-09** | **Breaking:** Innovation Use now requires investment data for every `contributing_bilateral_projects[]` entry. Send exactly one: a positive `usd_budget`, or `is_determined: true`. | **Yes, for Innovation Use.** `usd_budget: 0`, `is_determined: false` alone, an omitted pair, or sending<br>both values is rejected before the result reaches Reporting. |
| **2026-09** | **New:** `keep_editing` in `data` — optional boolean. `true` creates the result in PRMS Reporting as **Editing** instead of **Pending review**, so the reporting user completes the non-MDS fields in PRMS and submits it from there. Absent or `false` keeps today's behaviour. |  None. Opt in **per result**, inside `data` — a flag sent at the top level of the request never reaches validation. See **keep_editing** below. |
| **2026-08** | **Breaking:** `evidence[].link` must carry an `http(s)` scheme, and links hosted on file storage platforms (SharePoint, OneDrive, Google Drive, Dropbox) are rejected. | **Yes.** Stop sending storage links and bare file names — both used to be accepted. See **Evidence links** below. |
| **2026-08** | `innovation_use` actors: `actor_type_name` is now resolved against the actor type catalogue. An unresolvable name or id is rejected. | **Yes, if you send names.** An actor identified by name alone was previously **dropped without any error**. See **Innovation use — actors** below. |
| **2026-08** | `innovation_use` actors: `women_youth` / `men_youth` are validated against their sex total and rejected when greater. | **Yes.** Check the figures before submitting. Youth is a subset of each sex, not a separate group. |
| **2026-08** | Conditional validation corrected across `common_fields`, `knowledge_product` and `innovation_use`. Several conditions used to fire when a field was **absent**, demanding fields that were never actually required. | **None.** Payloads that were wrongly rejected now pass. Nothing that was accepted before is rejected now. |
| **2026-08** | `external_reference` is returned on **every** row of the ingest response, including rows that failed and rows rejected before processing. The previously documented path now exists. | **None.** See the updated table in **external_reference**. |
| **2026-08** | **New:** `external_reference` in `data` — your own identifier for the result (consecutive, UUID, any string). Optional. Stored verbatim and returned verbatim on the decision webhook and in the ingest response. | None to keep ingesting. **Required in practice if you want to use webhooks**: without it a callback carries no field pointing at your record. |
| **2026-08** | **New:** self-service **decision webhooks**. Register an HTTPS callback with `POST /webhook` using your existing API key, and PRMS notifies you when a Science Program approves or rejects one of your results. See **[Webhooks](#tag/webhooks)**. | None to keep ingesting. To receive decisions, register a callback **before your results go under review** — decisions taken with no destination registered are not replayed. |
| **2026-08** | `lead_contact_person` (with `email` + `name`) is now **mandatory** in `data` for all result types. | Producers must add it to every payload, otherwise the request is rejected at validation (`(root) must have required property 'lead_contact_person'`). |
